# Issue #5 SEO Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 公開URLと各ページのSEO情報を統一し、RSS・sitemap・robots.txtを生成物で自動検査できるようにする。

**Architecture:** Astroの既存レイアウトとエンドポイントを保ち、純粋関数でURL・SEO値を決める。Sanity未接続でも動くfallbackビルドの生成物をCIで検査し、値の分岐はNodeの単体テストで固定する。

**Tech Stack:** Astro 5、TypeScript、Sanity、`@astrojs/rss`、`@astrojs/sitemap`、Node 24 `node:test`。新規依存は追加しない。

**Spec:** `docs/superpowers/specs/2026-10-23-issue-5-seo-design.md`

## Global Constraints

- Astroの静的生成、Sanityのビルド時取得、S3 + CloudFront配信を維持する。
- 本番の正規URLは `PUBLIC_SITE_URL=https://pet.blog.uribou.me`。Sanityの `siteUrl` は編集互換のため残す。
- 404はnoindex・sitemap除外。通常ページと公開記事は検索対象。RSSは公開記事のみ。
- 本番Sanityへの書き込み、コンテンツ公開、AWS設定変更、URL移行はしない。
- 作業は `feat/issue-5-seo` の既存worktreeで行い、Issueタスク資源はPRのレビューが終わるまで保持する。

## Review Focus

- `PUBLIC_SITE_URL` が欠落・HTTP・サブパス・クエリ付きの本番ビルドを拒否し、ローカルの既定値は壊さないか → Task 1の検証テスト。
- Sanityの `siteUrl` が異なる場合もcanonical・OGP・RSS・sitemap・robotsが一つの公開URLになるか → Task 1、3、4のテスト。
- 空白だけのSEO値や画像URLが既定値へ落ちるか → Task 2の単体テスト。
- 404だけがnoindexで、sitemapに非HTMLや404が紛れないか → Task 3と4の生成物テスト。
- 公開記事が0件でもRSSが生成でき、日時順とXMLエスケープが壊れないか → Task 3のRSS関数テストとTask 4の生成物テスト。

### Task 1: 公開URLを一箇所で検証・生成する

**Files:** Create `src/lib/siteUrl.ts`, `tests/site-url.test.mjs`。Modify `astro.config.mjs`, `src/lib/env.ts`, `src/layouts/BaseLayout.astro`, `src/pages/robots.txt.ts`。

**Interfaces:** `resolveSiteUrl(raw: string | undefined, fallbackMode: string | undefined): string` は末尾 `/` なしのoriginを返す。`siteUrlFor(path: string, siteUrl: string): string` はパスの絶対URLを返す。`publicSiteUrl` は同じ `resolveSiteUrl` から得る。

- [ ] `tests/site-url.test.mjs` に、末尾スラッシュ、通常ページ・XMLのURL、本番の欠落・HTTP・example.com・サブパス・クエリ・フラグメント・認証情報の拒否を追加する。ローカル既定値とHTTP localhostも確認する。
- [ ] `node --test tests/site-url.test.mjs` を実行し、未実装の関数を理由に失敗することを確認する。
- [ ] `src/lib/siteUrl.ts` に上記2関数を実装する。URLは`new URL()`で解析し、origin以外の入力を拒否する。`SANITY_FALLBACK_MODE=never`のみHTTPSと非example.comを必須にする。
- [ ] Astro設定と `src/lib/env.ts` がこの関数を使うようにし、レイアウトのcanonical・robotsのsitemap参照を `publicSiteUrl` に寄せる。
- [ ] `node --test tests/site-url.test.mjs` と `pnpm build` をオフラインfallbackで通す。
- [ ] このTaskの変更をコミットする。

### Task 3: RSS・sitemap・robotsの集合とURLを固定する

**Files:** Create `src/lib/rss.ts`, `tests/rss.test.mjs`。Modify `src/pages/rss.xml.ts`, `astro.config.mjs`, `src/pages/robots.txt.ts`。

**Interfaces:** `rssItems(posts: PostSummary[], siteUrl: string)` は `@astrojs/rss` に渡すitem配列を返す。順序は取得済みの公開日時降順を保ち、各linkは `siteUrlFor` で絶対URLにする。

- [ ] `tests/rss.test.mjs` に公開日時順、空配列、`seoDescription → excerpt` の優先順位、絶対リンク、特殊文字を含むRSS出力を追加し、失敗を確認する。
- [ ] `rssItems` とRSSエンドポイントを実装し、日本語のフィードを設定する。sitemap統合の `filter` で `/404.html` とRSS・robots等の非HTMLを除く。robotsはTask 1の公開URLを参照する。
- [ ] `node --test tests/rss.test.mjs`、オフラインfallbackの `pnpm build` を通し、生成されたRSS・sitemap・robotsの実際のルート名を確認する。
- [ ] このTaskの変更をコミットする。

### Task 4: 生成物のSEO検査をCIと運用文書に組み込む
